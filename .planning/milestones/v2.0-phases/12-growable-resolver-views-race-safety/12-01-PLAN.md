<objective>
Make the compiler's file-resolution view grow as protos are demanded, incrementally and under
one lock, and prove it with a number rather than a code reading.

Purpose: after Phase 11 the compiler's `Parser.FilesResolver` is frozen at construction over the
~65 seeded well-known types, so every proto `ParseOne` loads mid-compile is invisible to it
(RSLV-01). The naive fix — re-running `GetFilesResolver()` on a miss — reintroduces the
O(everything-loaded-so-far) rebuild this milestone deleted, so growth must be
`(*protoregistry.Files).RegisterFile`, one call per newly recorded file (RSLV-02).
`protoregistry.Files` has zero internal synchronization for a locally-constructed instance, so the
moment it starts growing, `ParseFilesX`'s unlocked read of it becomes a real data race that
`go test -race` will catch in the already-shipped `TestConcurrentCompile` — which is why the
locked read lands in this plan, not a later one.

Output: a growable, `d.mu`-guarded `filesResolver` on `DescriptorRegistry`; growth wired into the
two existing write paths; locked accessors; the `ParseFilesX` read rerouted through them; and two
tests that pin both halves of RSLV-02 (no rebuild, no re-registration).
</objective>

- **D-01 (hybrid):** only `FilesResolver` grows, by real incremental registration.
  `RegistryTypeResolver` (`compiler/lib/parser/parser.go:48-116`) is **not** touched — it already

**Discretion resolved in this plan, on code evidence:**
- *Locking / API shape:* the growable `*protoregistry.Files` lives on `DescriptorRegistry` under
  the existing `d.mu`, not in a parser-owned wrapper with its own mutex. `recordFileLocked`
  already runs under `d.mu.Lock()` on every write path, so there is no scenario where the resolver
  is written independently of `FileRegistry`; a second lock would add ordering discipline for zero
  benefit.
- *`Parser.FilesResolver`'s field type stays `*protoregistry.Files`.* Evidence: a full-tree grep
  finds exactly two non-construction readers — `server/server.go:292-297,426,433` (always an
  eager, `ImportPaths`-empty registry, guarded by the existing
  `TestDiscoveryScanDoesNotBackReflection`) and `compiler/lib/parser/parser.go:123`. Only the
  second can observe a growing resolver, and it is fixed in this plan. An interface change would
  ripple through four packages and fix zero additional races.
- *Registration granularity:* the whole transitive closure, because `recordFileLocked`'s existing
  recursion already computes it and its already-present guard already prevents double
  registration. Registering only the top-level file would let the two sets diverge the moment a
  transitively-loaded dependency is later named directly.
- *Research Open Question 1 — resolved YES:* the counter is paired with a registration-**error**
  count, asserted to be 0. A `RegisterFile` duplicate error that is only logged would mask the
  Pitfall-3 divergence bug even when the final sets happen to be correct.
</locked_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Concurrent compile goroutines → one shared `*protoregistry.Files` | `compiler/service.go`'s `CompileFiles` handler and `compiler/command.go`'s `runLocally` both fan out `errgroup.Go` per file against one shared `*lib.Compiler`, hence one `DescriptorRegistry` and one resolver object. This plan turns that object from read-only into read-write. |
| `.proto` files under `src/` → the growable resolver | Repo-local, already-trusted input. This plan changes how their descriptors are exposed to readers, not what is trusted or parsed. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-01 | Denial of Service | `DescriptorRegistry.filesResolver` (`*protoregistry.Files`) accessed without `d.mu` | high | mitigate | Every `RegisterFile` runs under the `d.mu.Lock()` `recordFileLocked`/`ParseAll` already hold; every `FindFileByPath`/`RangeFiles` runs under `d.mu.RLock()` in the new accessors; `ParseFilesX`'s unlocked read is rerouted through them in Task 1.
