<objective>
Put the mutation server on the lazy construction path without regressing either of the two
things laziness would otherwise break: `MutateConfig`'s ability to marshal a custom type,
and gRPC reflection's ability to describe every service the server exposes.

Purpose: under lazy construction the serving parser's construction-time snapshot is
near-empty, so leaving `MutateConfig` on it would hard-fail every custom-type mutation
(D-03), and leaving reflection on the growable serving resolver would let a client list a
service by name and then fail to describe it — a user-visible grpcui regression the phase
goal forbids (D-06).
Output: three line-level changes in `Init`/`MutateConfig`/`NewProtoconfMutationServer`, the
hand-registered well-known files mirrored onto the retained discovery resolver, and a
reflection round-trip test that fails if either half regresses.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gRPC client → `MutateConfig` | An untrusted `ConfigMutationRequest` carries a caller-chosen `Path` and an `Any` with a caller-chosen type URL |
| gRPC client → `ServerReflection` | An unauthenticated-by-default introspection surface enumerating every descriptor the resolver holds |
| `src/*.proto` on disk → `Init`'s discovery parse | Repository-authored protos are parsed eagerly at server start |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-06 | Denial of Service | `MutateConfig`'s marshal resolver, now tiered | high | mitigate | D-02 moves a resolution failure from process start to first request, so a caller-supplied unknown type URL now does on-demand work inside the handler. That work is bounded: the scan tier is hard-capped at `scanCandidateLimit = 32` candidate parses per lookup (`utils/symbol_scan.go:42`), and the symbol index is built at most once per registry (`ensureSymbolIndex` is singleflighted and content-key cached under `.protoconf_cache`). Plan 14-06's tight-loop and e2e tests exercise this path under concurrency. |
| T-14-07 | Information Disclosure | Reflection `DescriptorResolver` = `discoveryFiles` | medium | accept | Reflection now discloses every proto under `src/` regardless of what any config demanded. This is byte-identical to the pre-lazy behavior the phase goal requires preserving, sits behind the same `bearerTokenInterceptor` auth path as every other RPC, and exposes schema rather than data. Narrowing it would reintroduce the describe-after-list regression D-06 exists to prevent. |
| T-14-08 | Tampering | Retained discovery registry (D-04) | medium | mitigate | The registry is held only as an `Init`-local variable captured by the reflection servers' own references; no struct field is added, so no method on `ProtoconfMutationServer` can reach it. Acceptance criteria assert the absence of such a field, and plan 14-05's repo-wide end-state gate asserts no second general resolution source survives. |
| T-14-SC | Tampering | npm/pip/cargo installs | high | mitigate | Zero dependencies added; `git diff --exit-code go.mod go.sum` must be clean at plan end. RESEARCH.md § Package Legitimacy Audit records "No new packages" for the phase. |
