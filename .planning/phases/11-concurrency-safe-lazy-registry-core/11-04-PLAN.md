<objective>
Close `G-11-3`: `protoconf mod tidy` panics with `assignment to entry in nil map` when
`protoconf.lock` omits the `deps` key. Restore the non-nil-`Deps` invariant at the one chokepoint
every caller routes through, stop `Init` from discarding its own merge, and prove `mod sync`'s
`.fds` bytes survive a concurrent in-process lazy compile — the one UAT backstop truth the panic
prevented anyone from observing.

**`G-11-3` is PRE-EXISTING, not a Phase 11 regression.** It reproduces identically on `b69e3b2`,
the commit before Phase 11 began; the line number moved only because Phase 11 added lines above
it. It is being closed under Phase 11 by explicit user decision, so the requirements ledger must
not attribute it to LAZY-01..05 or CONS-01. This plan's `requirements: [LAZY-04]` covers Task 2
only; Task 1 is tracked by `gap_ids: [G-11-3]`.

Purpose: `LoadFromLockFile` is the only site that unmarshals into `m.head`, and
`protojson.Unmarshal` resets its destination before populating it. A lock file with no `deps` key
therefore leaves `m.head.Deps` nil, destroying the invariant `NewModuleService` establishes, and
`Init`'s `m.head.Deps[name] = msg` panics. That violates CLAUDE.md's "no panics in production
code". Eight production call sites route through this one function, so the fix belongs there and
nowhere else — scattering nil-checks into callers would leave the ninth caller broken.

Output: a three-edit fix in `compiler/lib/module_service.go`, one deletion in `mod/command.go`,
a table-driven CLI-level regression test that pins every lock-file shape, and a concurrency test
that closes the UAT item-3 backstop.
</objective>

<prior_investigation>
The fix shape below was validated end-to-end before this plan was written, using `go build
-overlay` against a throwaway copy of the two source files. **These are observed results, not
predictions** — the executor should reproduce them, not re-derive them.

Behaviour of `mod init` against a `CONFIGSPACE` declaring one `remote_repo`, per lock-file shape:

| `protoconf.lock` | today | after this plan |
|---|---|---|
| `{"url":"."}` | panic, exit 2 | exit 0, dependency persisted |
| `{}` | panic, exit 2 | exit 0, dependency persisted |
| `{"url":".","deps":{}}` | **exit 0, persists nothing** | exit 0, dependency persisted |
| absent | exit 0, dependency persisted | exit 0, dependency persisted |
| zero bytes | panic, exit 2 | exit 1, `proto: syntax error (line 1:1)`, file untouched |
| `{"url": ` (truncated) | panic, exit 2 | exit 1, `proto: unexpected EOF`, file untouched |
| `{"url":".","bogus":1}` | panic, exit 2 | exit 1, unknown-field error, file untouched |

Three separate defects, one root cause:

1. **The panic.** `protojson.Unmarshal` resets `m.head`; a lock file with no `deps` key leaves
   `Deps` nil and `Init` writes into it.
2. **The silent no-op.** `MergeLock` calls `LoadFromLockFile` (reset) and then `Lock`, so `Init`'s
   `CONFIGSPACE` merge is discarded before it is written. The `{"deps":{}}` row isolates this
   symptom cleanly: it never panics, it just does nothing. Confirmed independently against the
   `utils/testdata/small` fixture — appending a new `remote_repo` to its `CONFIGSPACE` and running
   `mod init` leaves the lock file without it.
3. **The swallowed error.** `modInitCommand.Run` calls `LoadFromLockFile` and ignores the result,
   so a malformed lock file reached `Init` with a half-reset `head`. Restoring the invariant alone
   is not enough here: a variant that fixed only `LoadFromLockFile` and `MergeLock` turned the
   panic into `mod init` exiting 0 having **overwritten the corrupt lock file** with a fresh one —
   strictly worse for the operator than the crash. That is what prohibition 1 forbids.

The chosen shape moves the load to the top of `Init`, which makes `Init` self-sufficient, makes
the redundant call in `modInitCommand.Run` dead, and surfaces the parse error to the operator
through `Init`'s own return value. Under this shape the full suite is green
(`go test $(go list ./... | grep -v '/agent$')`, all 18 packages `ok`), including
`compiler/lib`, `server`, `inserter`, `mutate` and `test` (e2e), whose `Init` callers do **not**
pre-load the lock file.

Adjacency, observed: a lock entry `r` at `./internal/OLD.tgz` with `integrity: h1:STALEVALUE=`
and `fileDescriptorSetSum: deadbeef`, plus a `CONFIGSPACE` declaring `r` at `./internal/NEW.tgz`,
merges to ONE entry with `url` = NEW, `integrity` absent (cleared because `GetterUrl` changed) and
`fileDescriptorSetSum` = `deadbeef` preserved.

Encoding, observed: `protojson` deliberately varies its whitespace between builds
(`"url": "."` in one binary, `"url":  "."` in another) while sorting `deps` keys. Assertions on
the lock file must parse it or match keys — never compare bytes across builds.
</prior_investigation>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `protoconf.lock` on disk → `ModuleService.LoadFromLockFile` | An attacker- or accident-influenceable file is unmarshalled by `protojson` into `m.head`.
