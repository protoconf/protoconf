```protobuf
syntax = "proto3";
package protoconf.server.config.v1;
option go_package = "github.com/protoconf/protoconf/server/config/v1;protoconf_server_config";

message ServerConfig {
    string grpc_address = 1 [json_name = "grpc-address"];
    string pre_mutation_script = 2 [json_name = "pre"];
    string post_mutation_script = 3 [json_name = "post"];
    string tls_cert = 4 [json_name = "tls-cert"];
    string tls_key = 5 [json_name = "tls-key"];
    string tls_ca = 6 [json_name = "tls-ca"];
    string auth_token = 7 [json_name = "auth-token"];
}
```

**inserter/config/v1/inserter_config.proto** (per D-01, D-07, PCLI-03):
Create directory `inserter/config/v1/` and write `inserter_config.proto`:
```protobuf
syntax = "proto3";
package protoconf.inserter.config.v1;
option go_package = "github.com/protoconf/protoconf/inserter/config/v1;protoconf_inserter_config";

message InserterConfig {
    string store = 1;
    string store_address = 2 [json_name = "store-address"];
    string prefix = 3;
    string namespace = 4;
    bool delete = 5 [json_name = "d"];
}
```
IMPORTANT: `store` is a plain `string` (not an enum) and `store_address` is a single `string` (not repeated). This exactly matches the current `command.KVStoreConfig` Go struct where `Store` is `string` and `Address` is `string`. The research recommended an enum and repeated string, but the actual code uses simple strings. Using `string` ensures Phase 8 PopulateFlagSet wiring is trivial and backward compatible.

Per discretion, NOT defining a StoreType enum here — the current code uses string constants, and defining an enum would require Phase 8 to handle string-to-enum conversion. Keeping it as `string` is the simplest path that matches the existing flag interface exactly.
