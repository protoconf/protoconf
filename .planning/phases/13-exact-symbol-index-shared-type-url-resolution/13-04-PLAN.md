<objective>
Close CONS-05: make the mutable-config load path resolve its value's type — and
every `Any` nested inside that value — through the one shared resolution chain,
by removing `loadMutable`'s direct reach into the module service's registry.

Purpose: this is the in-scope divergence CONTEXT.md D-03 names. Even with the
scan and index tiers wired into `RegistryTypeResolver`, this one call site never
reaches them; a mutable config carrying a type whose file nothing else loaded
still fails here. It is a same-tier bypass, three lines below a call that already
does the right thing.

Output: one resolution instead of two, both routed through
`l.parser.TypeResolver`, plus the end-to-end regression test that would have
caught the bypass.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `mutable_config/*.materialized_JSON` -> `loadMutable` | A JSON file on disk, written by the mutation server at runtime rather than by a developer, supplies the `@type` strings this path resolves. It is the least developer-reviewed input in the compile pipeline. |
| resolved type -> Starlark value | The resolved descriptor becomes a `starproto` message a `.pconf` can read fields from. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-13-15 | Spoofing | a mutable config naming a `@type` that resolves to a different message than intended | medium | mitigate | Routing through `RegistryTypeResolver` puts this input behind the same verify-after-parse discipline as every other resolution: a scan or index candidate is only accepted after `ParseOne` loads it and the registry re-check succeeds.
