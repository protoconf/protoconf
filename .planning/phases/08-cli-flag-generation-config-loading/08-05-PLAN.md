<why_provenance_and_not_a_comparison_patch>
Read this before writing any code. It is the difference between a third failed attempt and a fix.

**1. `base` is an accumulator, so no comparison against it can answer the provenance question.**
`LayerConfigFile` mutates `base` with `proto.Merge(base, live)` on every call, so after file 1 the "baseline" contains file 1's raw values. When file 2 arrives, a field whose env value happens to equal file 1's value compares equal to the baseline and is discarded as "unchanged". `08-REVIEW.md` traces the alternative — comparing against a pristine never-mutated snapshot — and shows it breaks `second_file_overrides_first` and `later_config_file_wins`, because a value carried over from an earlier file then looks explicit and becomes permanently sticky. Value equality against ONE baseline cannot separate the two cases. Two baselines can: the pristine defaults tell you what the compiled-in value was, and a separate record of what env/flags supplied tells you what must win. This plan keeps both, and keeps the accumulated file layer as a third, separate message.

**2. The provenance signal is available and is not a guess.**
- **Env vars:** `libprotoconf`'s `Environment()` writes into the live message before any flag or config file is parsed, so `preFile` on the FIRST `LayerConfigFile` call differs from the factory defaults exactly on the fields env supplied. Recording that difference once, on the first call, is the "field-number set captured immediately after `lpc.Environment()`" that 08-VERIFICATION.md's gap 1(a) asks for.
- **Flags:** verified against Go 1.25.1 `flag.parseOne` — `f.actual[name] = flag` is written AFTER `flag.Value.Set(value)` returns. So calling `fs.Visit` from inside the `-config-file` `flag.Func` callback enumerates exactly the flags parsed strictly before this `-config-file` occurrence. Empirically confirmed: parsing `-grpc-address :7777 -config-file a.json -config-file b.json` makes the first callback see `[grpc-address]` and the second see `[config-file grpc-address]`. That is precise flag provenance, not an inference, and it is what makes a flag whose value equals the factory default still win.
- Flag names map to fields by `fd.JSONName()`, because `libprotoconf`'s `PopulateFlagSet` registers each top-level flag under exactly `f.JSONName()`. Names that match no field (notably `config-file` itself, seen from the second occurrence onward) are ignored.

**3. Only TOP-LEVEL flags can carry provenance, and that is correct.**
`PopulateFlagSet` handles a `MessageKind` field by building a *detached* `dynamicpb` message and registering that message's flags on the parent flag set. So `-tls-config-cert-file` writes into a throwaway message and has no effect on `c.config` at all today. Do not attempt to map nested flag names onto nested fields, and do not add a test asserting that `-tls-config-cert-file` works — it does not, that is a pre-existing libprotoconf limitation outside this phase's gaps, and asserting it would fail. Provenance is keyed by TOP-LEVEL field number only.

**4. `proto.Merge` still appends to repeated fields.** Confirmed in 08-03. Every place a config file's values are folded into the accumulator, or the accumulator into the result, must correct map and list fields through `setFieldReplacing` immediately afterwards.

**5. Recursive submessage merge is what makes later-file-wins work for message fields.** Folding file 2's `TlsConfig{cert: cert_file "b.pem"}` into an accumulator already holding `TlsConfig{cert: cert_file "a.pem"}` with `proto.Merge` sets the source's oneof case, yielding `b.pem`, while a file that sets only `key_file` leaves `cert_file` intact. That is the desired semantics; keep `proto.Merge` for the fold and do NOT replace message fields wholesale.

**6. The whole design was executed against the real protos before this plan was written.** A throwaway probe (created, run, deleted, not committed) exercised the exact algorithm below against `ServerConfig`, `InserterConfig` and `AgentConfig`: both reproduced gap scenarios flipped to the correct result, and all twelve existing `TestLayerConfigFile` expectations still held. The algorithm in Task 1 is that probe, not a sketch.
</why_provenance_and_not_a_comparison_patch>

<library_facts>
Verified directly against `github.com/protoconf/libprotoconf@v0.1.0` source in the module cache and against Go 1.25.1's `flag` package. Do not re-derive these; do re-check any that the implementation appears to contradict, and record the discrepancy in the SUMMARY.

1. `configtool.NewConfig(p)` stores `p` as `Config.msg`. `flaggable.Set` and `Environment()` both write through `f.cfg.msg` / `c.msg`, resolved at call time. Reassigning the component's `config` pointer orphans the flag set — this is why the live message must be mutated in place.
2. `Config.Unmarshal` dispatches on file extension to `protojson.Unmarshal(data, c.msg)` (`.json`), `yaml`→JSON→`protojson` (`.yaml`/`.yml`), `prototext.Unmarshal` (`.pb`), `proto.Unmarshal` (`.data`), and jsonnet→JSON (`.jsonnet`). All of those RESET the destination message first, so immediately after `lpc.Unmarshal` the live message holds only this file's values.
3. `Config.Environment()` iterates TOP-LEVEL fields only and skips any variable whose value is the empty string. It never descends into a message-typed field, so `PROTOCONF_AGENT_TLS_CONFIG_CERT_FILE` is advertised in `--help` but never read. Out of scope; do not try to fix it and do not assert on it.
4. `Config.PopulateFlagSet` registers each top-level flag under `f.JSONName()`. For a `MessageKind` field it builds a detached `dynamicpb` message and copies that message's `flag.Value`s onto the parent flag set under `<parent JSONName>-<child name>`, so those nested flags do not write into the component config.
5. Go 1.25.1 `flag.(*FlagSet).parseOne` records `f.actual[name] = flag` AFTER `flag.Value.Set` returns. `Visit` therefore enumerates only flags fully parsed before the current one.
6. `protojson` honours `json_name`, including nested ones: `{"tls-config":{"cert-file":"a.pem"},"store-tls":{"ca-file":"ca.pem"}}` unmarshals into `AgentConfig.TlsConfig.CertFile` and `AgentConfig.StoreTls.CaFile`. Confirmed by execution.
7. `proto.Merge` overwrites scalars, APPENDS repeated fields, and merges submessages recursively (setting the source's oneof case when the source has one).
8. `github.com/protoconf/protoconf/agent/config/v1` has no repository-internal dependencies (`go list -deps` returns only itself), so `package command` may import it in a test without creating an import cycle.
</library_facts>

    1. `l.markExplicitFlags()` — exact flag provenance for flags already parsed.
    2. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator environment → process config | `PROTOCONF_AGENT_*` variables are read by `lpc.Environment()` and become authoritative configuration. Whoever controls the process environment (shell wrapper, Dockerfile `ENV`, Kubernetes pod spec) crosses here. |
| config file(s) on disk → process config | `-config-file` is repeatable; each occurrence reads an operator-named path via `os.ReadFile` and decodes it into the config message. Two files can disagree about the same field. |
| CLI argv → process config | Flags parsed by `flag.Parse`; highest precedence by design. |
| resolved config → TLS material | `AgentConfig.tls_config` and `store_tls` select the certificate, key and CA the agent presents to subscribers and uses against the KV store. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-05-01 | Spoofing | `AgentConfig.tls_config` resolution in `command/configfile.go` | high | mitigate | THE GAP-2 DEFECT. `protoconf agent -config-file base.json -config-file override.json` silently keeps `base.json`'s `cert-file`/`key-file`, so an operator narrowing or rotating TLS material via a later, more specific file gets the older identity with no warning — the agent presents a certificate the operator believes it retired. Mitigated by the provenance rewrite in Task 1 and pinned by the `later_file_wins_for_tls_cert_file` CLI row and the `later_file_wins_for_message_field` unit row. `security_block_on: high` means this threat's mitigation is a release gate for the phase. |
| T-08-05-02 | Tampering | `AgentConfig.store_tls` resolution | high | mitigate | Same defect on the KV-store side: a later file's `ca-file` is discarded, so the agent may validate the store connection against a CA the operator intended to replace, widening who can impersonate the KV store. Mitigated identically; pinned by `later_file_wins_for_store_tls_ca_file`. |
| T-08-05-03 | Elevation of Privilege | env-var provenance in `command/configfile.go` | medium | mitigate | THE GAP-1 DEFECT. A `PROTOCONF_AGENT_*` value silently loses to a config file whenever an earlier file coincidentally set the same value — so an operator pinning an address, prefix or token through the environment (the mechanism a container runtime controls) can be overridden by file contents they may not control. Mitigated by recording provenance once instead of inferring it; pinned by `env_wins_over_two_files_when_first_file_coincides`. |
| T-08-05-04 | Information Disclosure | `agent/command_test.go`, `command/configfile_test.go` | low | mitigate | Precedence fixtures use only address strings and non-existent `.pem` FILENAMES (`a.pem`, `b.pem`, `ca1.pem`) — never key or certificate CONTENT, and never the `-text` variants of the TLS oneofs. Config files are written into `t.TempDir()` (auto-removed), never `os.TempDir()`. |
| T-08-05-05 | Repudiation | precedence resolution | low | accept | Nothing logs which source won for a given field, so a support investigation cannot reconstruct why a value took effect. Accepted for this gap closure: adding per-field provenance logging is new surface beyond the two gaps, and `--help` plus `CHANGELOG.md` document the ordering. Revisit if operators report precedence confusion. |
| T-08-05-06 | Denial of Service | `-config-file` handler | low | accept | `os.ReadFile` on an operator-supplied path reads the whole file into memory with no size cap, and `-config-file` is repeatable. Pre-existing on all five components, unchanged by this plan, and the paths are supplied by whoever starts the process. |
| T-08-05-SC | Tampering (supply chain) | Go module graph | high | mitigate | This plan installs nothing: there is no npm/pip/cargo step, and every symbol used (`flag`, `google.golang.org/protobuf/proto`, `.../reflect/protoreflect`) is stdlib or an existing direct dependency. No `## Package Legitimacy Audit` is required because there are no package-manager installs. Enforced by the `git diff --exit-code go.mod go.sum` gate in Task 1's `<verify>`. |

Canon-referral breadcrumbs (surfaced, deliberately not minted as prohibitions): config-input trust ordering, credential-bearing configuration fields, and arbitrary-path file reads are canon security territory covered by `/gsd-secure-phase` and the register above, not by bespoke prohibitions.
