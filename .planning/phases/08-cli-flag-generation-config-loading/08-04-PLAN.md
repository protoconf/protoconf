This is the accepted trade-off of the user's locked decision: PCLI-09 and ROADMAP Success Criterion #5 both state env-over-file, and env-over-file is the conventional twelve-factor ordering. **Enum specifics, verified against `libprotoconf@v0.1.0` `flagset.go` and the generated `InserterConfig` — do not re-derive:**
- The env key comes from `toEnvKey(prefix, string(fd.Name()))` on the PROTO field name `store`, giving exactly `PROTOCONF_INSERTER_STORE`. The flag name comes from `f.JSONName()`, which is `store` since the field carries no `json_name` override.
- `flaggable.detect` resolves an enum by `values.ByName(protoreflect.Name(value))`, so the env/flag value must be the enum value name **exactly as declared** — lowercase `consul`, `etcd`, `zookeeper`, `configmaps`. An unknown name returns an error, not a silent zero.
- `protojson` accepts the same names in the config file: `{"store": "zookeeper"}`.
- `inserter/inserter.go` constructs `&InserterConfig{}` with NO factory defaults, so `store` starts at `consul` (number 0).
- **Verified proto3 presence behavior:** on a freshly built message `Has(store)` is `false`; after a reflective `Set(store, etcd)` it is `true`; after `Set(store, consul)` it is still `false`. `Message.Range` therefore visits `store` in the first case and never in the second.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator environment → agent config | `PROTOCONF_AGENT_*` variables become authoritative over a config file. In this project's supported deployment models the environment is set by the pod spec (Kubernetes), by `ENV`/`--env` (the scratch Docker image), or by the invoking shell. |
| ConfigMap / mounted file → agent config | `-config-file` typically points at a mounted Kubernetes ConfigMap or a file baked into an image; it is now the LOWER-priority source of the two. |
| operator environment → mutate/compiler/inserter config | Same shape, short-lived CLI processes rather than long-running servers. |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-04 | Elevation of Privilege | `agent/command.go` precedence reversal | medium | accept | In a Kubernetes deployment, `env:` and `volumeMounts:` of a Pod are edited by the same principal (whoever can update the Deployment), so the reordering grants no new capability.
