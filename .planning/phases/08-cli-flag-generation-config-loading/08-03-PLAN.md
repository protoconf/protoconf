<why_not_the_one_line_reversal>
The obvious fix — flipping `proto.Merge(orig, c.config)` to `proto.Merge(c.config, orig)` — is **wrong in two ways**, both verified by reading the sources. Do not take the shortcut.

**1. `orig` also carries the factory defaults, so a bare reversal makes config files inert.**
`server/server.go` constructs its config with `GrpcAddress: consts.ServerDefaultAddress`. `orig := proto.Clone(c.config)` therefore contains `:4301` even when no env var is set. Merging `orig` on top of the file state copies that non-zero default over the file's value, so `protoconf serve -config-file s.json` would silently ignore `grpcAddress` in `s.json`. That breaks the `config file > proto defaults` half of PCLI-09 while fixing the `env > file` half. Same trap in `mutate/mutate.go` (`ProtoconfRoot`, `ServerAddress`) and `agent/command.go` (`GrpcAddress`, `HttpAddress`).

**2. Reassigning `c.config` unbinds the flag set, so flags cannot beat anything parsed after them.**
In `github.com/protoconf/libprotoconf@v0.1.0`, `NewConfig(p)` stores the message pointer as `Config.msg`; the `flaggable` values installed by `PopulateFlagSet` resolve `f.cfg.msg` at `Set()` time, and `Environment()` writes through the same field. So the flag set and the env loader permanently write into the message that was passed to `NewConfig`. The current `c.config, _ = orig.(*ServerConfig)` points `cliCommand.config` at a *clone*, so every flag parsed after `-config-file` lands in the orphaned original and is discarded. The fix must update the original message **in place** and never reassign `c.config`.

**3. `Unmarshal` resets the live message.** `Config.Unmarshal` dispatches on file extension into `protojson.Unmarshal(data, c.msg)` (and friends), and `protojson.Unmarshal` resets the destination first. So immediately after `lpc.Unmarshal` the live message holds *only* the file's values — that is the layering input, and defaults/env/earlier-flags must be re-applied around it.

**The layering this plan implements** (helper does it once, all five components call it):

```
layer 0  factory defaults          (snapshot taken before lpc.Environment())
layer 1  config file values        (overwrite defaults; later -config-file overwrites earlier)
layer 2  env vars + flags parsed before -config-file   (any field differing from layer 0/1 base)
layer 3  flags parsed after -config-file  (written straight into the live message by flag.Parse)
```

"Explicitly supplied" is detected as *differs from the base* (defaults plus every config file loaded so far). Two consequences are real and must be stated rather than hidden: an env var whose value is exactly the factory default is indistinguishable from unset, and a proto3 scalar set to its zero value (empty string, `false`, enum 0) is indistinguishable from unset. Both are covered by explicit truths and tests below.
</why_not_the_one_line_reversal>

<library_facts>
Verified in `github.com/protoconf/libprotoconf@v0.1.0` (module dependency, already in `go.mod`) — do not re-derive:

- `environment.go` — `Environment()` iterates the message's fields and, **only when `os.Getenv(key) != ""`**, sets the field. An env var set to the empty string is a no-op.
- `environment.go` — `toEnvKey(prefix, string(fd.Name()))`: the env key is built from the **proto field name**, NOT `json_name`, upper-cased with non-alphanumerics collapsed to `_`. So `grpc_address` under prefix `PROTOCONF_SERVER` is `PROTOCONF_SERVER_GRPC_ADDRESS`.
- `flagset.go` — `flaggable.Set` / `.String` dereference `f.cfg.msg` at call time; the flag set is bound to the message pointer handed to `NewConfig`, forever.
- `unmarshalers.go` — `Unmarshal` switches on the file extension (`.json`, `.yaml`/`.yml`, `.pb`, `.data`, `.b64`/`.base64`, `.jsonnet`, `.toml`) and errors with "cannot detect unmarshaller for: …" otherwise. The JSON path is `protojson.Unmarshal(data, c.msg)`, which resets `c.msg` before decoding.
- `protojson` accepts either the `json_name` (`"grpc-address"`) or the proto field name (`"grpc_address"`) as the JSON key.
</library_facts>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator environment → process config | `PROTOCONF_SERVER_*` variables are read by `lpc.Environment()` and become authoritative configuration. Whoever controls the process environment (shell wrapper, Dockerfile `ENV`, Kubernetes pod spec) crosses here. |
| config file on disk → process config | `-config-file` reads an arbitrary operator-named path via `os.ReadFile` and decodes it into the config message. |
| CLI argv → process config | Flags parsed by `flag.Parse`; highest precedence by design. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Elevation of Privilege | `server/server.go` config-file handler | medium | accept | Reordering makes env vars authoritative over a file an operator may have believed was authoritative, including `auth-token`, `tls-cert`, `tls-key`, `tls-ca`. Accepted because setting the process environment already implies control of the process (same principal that can set `PROTOCONF_SERVER_AUTH_TOKEN` can also pass `-auth-token` or replace the binary's arguments), and because before this change env vars already supplied every field the file omitted. Residual risk is a *precedence surprise*, not a new capability — which is why 08-04 records the change in `CHANGELOG.md` and every component's `--config-file` usage text states the ordering. |
| T-08-02 | Information Disclosure | `server/server_test.go`, `command/configfile_test.go` | low | mitigate | Precedence tests use only address/prefix strings as fixture values and write config files into `t.TempDir()` (auto-removed). No real token, key or certificate material appears in a fixture, and no fixture is written to a shared path such as `os.TempDir()`. |
| T-08-03 | Denial of Service | `-config-file` handler | low | accept | `os.ReadFile` on an operator-supplied path reads the whole file into memory with no size cap. Pre-existing on all five components, unchanged by this plan, and the path is supplied by the operator starting the process. |
| T-08-SC | Tampering (supply chain) | Go module graph | high | mitigate | This plan installs nothing: no npm/pip/cargo step exists, and the helper uses `google.golang.org/protobuf`, already a direct dependency.
