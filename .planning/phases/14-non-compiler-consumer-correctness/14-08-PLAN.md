<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied type URL → the tiered resolver | An unknown symbol drives scan-tier candidate parses and, on a miss, a symbol-index build over the import roots |
| `.protoconf_cache` on disk → the symbol index | A cached index is read back and served for symbol lookups |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-23 | Denial of Service | Unbounded memory growth in a long-running process | high | mitigate | This plan IS the control's proof. `TestLoadedFileCountSequenceGuard` asserts a bounded per-request delta and a total strictly below corpus size over one long-lived registry, and `TestLoadedFileCountEscalationGuard` asserts that a single index-tier escalation does not register the tree. Without these, a regression that quietly restores whole-tree loading would ship green. |
| T-14-24 | Denial of Service | Pathological scan cost from a crafted type URL | medium | mitigate | The scan tier returns no candidates once the count exceeds `scanCandidateLimit = 32`, so a symbol name matching many declarations costs a bounded walk rather than an unbounded parse burst. `TestLoadedFileCountEscalationGuard`'s 33-file fixture exercises exactly that boundary. |
| T-14-25 | Denial of Service | Index build triggered by a malformed or empty type URL | medium | mitigate | `LoadSymbolByIndex` returns false early for a name with no resolvable package-and-message shape, so an empty or malformed URL never pays for a whole-tree index build. `TestEmptyTypeURLResolvesNothingAndBuildsNoIndex` asserts `IndexBuildCount()` stays at `0`. |
| T-14-26 | Spoofing | Duplicate fully-qualified symbol across two files | low | accept | The index tie-breaks deterministically on the lexicographically smaller path, and `SymbolFile` matches on the exact fully-qualified name's bytes with no case folding or affix matching. A repository declaring the same symbol twice is a repository-authoring error, not an attacker-controlled input; the accepted risk is that one of two identically-named local declarations wins, deterministically. `TestDuplicateSymbolResolutionIsStable` pins the determinism. |
| T-14-SC | Tampering | npm/pip/cargo installs | high | mitigate | Zero dependencies added; `testify` and `utils/testdata` are already in the module. `git diff --exit-code go.mod go.sum` must be clean at plan end. |
</threat_model>
