<objective>
Close the one failed must-have from `12-VERIFICATION.md`: restore `ParseFilesX`'s ability to
resolve a file that lives only in the parser's raw `FilesResolver` — the mutation server's six
hand-registered well-known files — and ship the regression test that should have accompanied the
change in `12-01`.

Purpose: `12-01` rerouted `ParseFilesX`'s resolver read from the raw `p.FilesResolver` field to
`p.registry.FindFileByPath`. For an eager registry (`len(d.ImportPaths) == 0`, D-03)
`GetFilesResolver` never assigns `d.filesResolver`, so `FindFileByPath` returns
`ErrNoGrowableResolver` forever, the code treats that as "not found", falls into `ParseOne`, and
`ParseOne` fails with `ErrLazyParseDisabled`. The canonical-lookup and `desc.WrapFile` tail — the
exact code that exists to serve hand-registered external files — became unreachable for the only
registry shape it was written for. Independently reproduced by the verifier and by this planner:
an eager registry plus `p.FilesResolver.RegisterFile(grpc_health_v1.File_grpc_health_v1_health_proto)`
plus `p.ParseFilesX("grpc/health/v1/health.proto")` returns
`registry has no growable files resolver` joined with `on-demand parsing requires import paths`.
It is latent, not live: the only production caller (`compiler/lib/starlark_loader.go:211`) always
runs against the compiler's lazy registry, and `server/server.go`'s parser never calls
`ParseFilesX`. This is a contract fix plus its missing test, not an incident.

The gap has a documented second half: `12-02-SUMMARY.md` and `12-02-PLAN.md` cited
`go test -race ./server/...` (`TestDiscoveryScanDoesNotBackReflection`) as proof this truth held,
but that test calls `s.parser.FilesResolver.FindFileByPath` directly and never reaches
`ParseFilesX`. That miscitation is closed here by construction rather than by editing history:
every evidence command in this plan invokes `ParseFilesX`, the red gate makes the transition
observable, and a prohibition forbids inheriting the citation. `12-VERIFICATION.md` and
`12-REVIEW.md` already carry the permanent record of the false claim in the same directory, so no
prior SUMMARY is amended — a third copy of that record would buy nothing and would perturb the
`covered_digest` of a file the re-verification compares against.

Output: a four-line `errors.Is` fallback in `ParseFilesX`, and
`compiler/lib/parser/eager_resolver_fallback_test.go` proving it red-then-green.
</objective>
