<objective>
Prove the phase's third success criterion with tests that force the interleaving rather than
hoping for it, at both the level the production code actually runs at and the level where the
lock is easiest to drop.

Purpose: `protoregistry.Files` gates its only internal lock on `r == GlobalFiles`, so the
locally-constructed instance plan `12-01` starts growing has zero synchronization of its own. An
unguarded concurrent write to it is a Go fatal "concurrent map writes" that kills the process, not
a soft race — and CI already runs `go test -race ./...`, so this gate is enforcement rather than
aspiration. `TestConcurrentCompile` already races 8 goroutines against one shared `*lib.Compiler`,
but nothing in it touches the resolver view, and its goroutines spend most of their time parsing
rather than reading the resolver, so the read/write interleaving the detector needs to observe is
rare. Research Open Question 2 asked whether to extend the existing test or add a dedicated
lower-level one; this plan resolves it as **both**, for the stated reason that the extension
proves end-to-end correctness while only the dedicated tight-loop reader reliably forces the
`RegisterFile`-against-`RangeFiles` interleaving.

Output: a resolver-view assertion inside the production-shaped concurrency test, and a dedicated
`utils` test that races registration against enumeration directly.
</objective>

<locked_decisions>
- **Research Open Question 2 — resolved as "do both", confirming 12-VALIDATION.md's Wave 0 list.**
  Reason: `TestConcurrentCompile`'s goroutines each call `CompileFile`, which spends the bulk of
  its time inside `protoparse.ParseFiles` with no lock held; the window where one goroutine is
  inside `filesResolver.RegisterFile` while another is inside `FindFileByPath` is a small fraction
  of the run, so a dropped lock could pass on a lucky schedule. A dedicated test whose reader
  goroutine does nothing but call `RangeFiles`/`FindFileByPath` in a tight loop for the whole
  duration of N concurrent `ParseOne` calls makes that window nearly continuous. Neither test
  alone is sufficient: the dedicated one does not prove the production call shape is safe, and the
  end-to-end one does not reliably force the interleaving.
- **Discretion resolved — SAFE-01 test placement:** the dedicated test lives in `package utils`,
  in a new file `utils/growable_resolver_race_test.go`, because the growable field and the
  registration counters are unexported. This matches the existing convention already used by
  `utils/lazy_parse_canonical_test.go` and `utils/parse_all_deadlock_test.go`.
- **D-02:** the non-divergence invariant is asserted in the direction that matters — every key in
  `FileRegistry` is findable through the resolver. A strict count equality is deliberately not
  used: the one-time seed build runs `protodesc.NewFiles` over `desc.ToFileDescriptorSet`, which
  can legitimately pull in a transitive dependency, so the resolver may hold a superset. A
  superset is harmless; a missing entry is the bug.
</locked_decisions>

  <action>
Create `utils/growable_resolver_race_test.go` implementing `<behavior>` exactly. Imports: `fmt`,
`path/filepath`, `sync`, `testing`, `github.com/protoconf/protoconf/utils/testdata`,
`github.com/stretchr/testify/require`, `golang.org/x/sync/errgroup`,
`google.golang.org/protobuf/reflect/protoreflect`. The file is `package utils`, so it imports
neither `utils` nor `parser`.

Structure the readers so they cannot spin the CPU into starving the writers: a plain
`for { select { case <-done: return; default: } }` loop calling the accessor once per iteration is
correct here, because every accessor call takes and releases `d.mu.RLock()`, which yields. Do not
add a `time.Sleep`, a ticker, or any other pacing — a sleep in the reader is exactly the change
that makes the interleaving rare again and quietly turns this gate into a no-op.

Both readers must exit before the test returns. Use a `sync.WaitGroup` with `defer wg.Done()` in
each reader and `wg.Wait()` after `close(done)`; a leaked reader goroutine still calling into the
registry after the test function returns is itself a race the detector will report against an
unrelated test.

Do not assert on how many files a reader saw, on elapsed time, or on the order `RangeFiles`
yields. `protoregistry.Files` specifies no range order, and any of those assertions would make
this gate flaky.
