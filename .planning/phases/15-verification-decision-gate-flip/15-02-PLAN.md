<objective>
Write down the one operator-visible consequence of the lazy-loading milestone, in the two
places an operator actually reads.

Purpose: before lazy loading, every proto under `src/` was parsed and linked at startup, so a
syntax error in a proto that no config referenced still failed the compile. Under the lazy
registry that proto is never parsed, so it is never reported. GATE-03 asks for this to be
decided deliberately and documented — not silently absorbed. The decision is D-04: accepted,
with buf named as the answer, and with an honest caveat about what protoconf does not do.

Output: one `### ⚠ BREAKING CHANGES` bullet in `CHANGELOG.md` and one standing-behavior
section in `README.md`, mutually consistent.
</objective>

The bullet must carry four facts, in this order:

1. **What changed.** `protoconf compile` no longer parses or links every `.proto` under
   `src/`. It parses only the files a config transitively loads. A proto that no config
   reaches is never parsed.
2. **The consequence.** A syntax or reference error in an unreferenced proto used to fail the
   compile and no longer does. It now surfaces the first time a config actually loads that
   proto. Name the upside in the same breath, because it is the reason: startup cost is now
   proportional to what a config demands rather than to repository size (6.97s to
   sub-200ms on the 799-proto reference corpus, per BASELINE.md).
3. **What an operator should do instead.** Run `buf` against their own config repository for
   whole-tree proto validation. That is now buf's job, not the compiler's.
4. **The caveat, stated plainly and not softened.** protoconf's own CI runs `buf breaking`
   and does not run `buf lint`, and this repository's `buf.yaml` scopes to protoconf's own
   protos rather than to a downstream config repository. So this is something an operator
   sets up and runs themselves; protoconf does not do it for them. The bullet must not read
   as though whole-tree validation is already covered somewhere.

Do not add a test, a fixture, or a `.pconf` case anywhere in this task or this plan. D-06 is
an explicit negative decision: GATE-03 asks for a written decision, not a test, and the
underlying "only reached protos are parsed" behavior is already covered by the Phase 11 LAZY
tests.
